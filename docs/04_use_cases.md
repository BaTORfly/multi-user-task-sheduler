# Use Cases

## UC-01. Регистрация пользователя

| Поле | Описание |
| --- | --- |
| Актор | Guest |
| Цель | Создать учетную запись и получить доступ к системе. |
| Предусловия | Email не зарегистрирован, поля валидны. |
| Постусловия | Пользователь создан, опубликована email-команда welcome-письма. |
| Связанные требования | FR-AUTH-01, FR-EMAIL-01 |

Основной сценарий:

1. Клиент отправляет `POST /api/v1/auth/signup`.
2. Backend валидирует `first_name`, `last_name`, `email`, `password`.
3. Backend создает пользователя и роль.
4. Backend формирует access token и refresh token.
5. Backend публикует welcome email в `EMAIL_SENDING_TASKS`.
6. Клиент получает `201 Created`, access token и refresh cookie.

Альтернативы:

| Условие | Результат |
| --- | --- |
| Невалидные поля | `400 ValidationErrorResponse`. |
| Email уже занят | `409 ErrorResponse`. |
| Ошибка сериализации email-команды | `500 ErrorResponse`. |

## UC-02. Авторизация пользователя

| Поле | Описание |
| --- | --- |
| Актор | Guest |
| Цель | Получить access token для защищенных endpoint. |
| Предусловия | Пользователь существует. |
| Постусловия | Клиент получил access token и refresh cookie. |
| Связанные требования | FR-AUTH-04, FR-AUTH-05 |

Основной сценарий:

1. Клиент отправляет `POST /api/v1/auth/login`.
2. Backend проверяет email и пароль.
3. Backend формирует пару токенов.
4. Клиент получает `200 OK`, access token и refresh cookie.

Альтернативы:

| Условие | Результат |
| --- | --- |
| Пустой email или пароль | `400 ValidationErrorResponse`. |
| Неверные учетные данные | `401 ErrorResponse`. |

## UC-03. Создание задачи

| Поле | Описание |
| --- | --- |
| Актор | User/Admin |
| Цель | Добавить задачу в личный список. |
| Предусловия | Пользователь авторизован, `title` заполнен. |
| Постусловия | Задача сохранена и привязана к пользователю. |
| Связанные требования | FR-TASK-01 |

Основной сценарий:

1. Клиент отправляет `POST /api/v1/tasks` с Bearer token.
2. Backend определяет текущего пользователя.
3. Backend валидирует `TaskDto`.
4. Backend сохраняет задачу.
5. Клиент получает `201 Created` и созданный `TaskDto`.

Альтернативы:

| Условие | Результат |
| --- | --- |
| Нет или невалиден JWT | `401 ErrorResponse`. |
| `title` пустой | `400 ValidationErrorResponse`. |

## UC-04. Изменение задачи

| Поле | Описание |
| --- | --- |
| Актор | User/Admin |
| Цель | Обновить данные своей задачи. |
| Предусловия | Задача существует и принадлежит текущему пользователю. |
| Постусловия | Задача обновлена. |
| Связанные требования | FR-TASK-04, FR-TASK-06 |

Основной сценарий:

1. Клиент отправляет `PUT /api/v1/tasks/{taskId}`.
2. Backend проверяет владельца задачи.
3. Backend обновляет `title`, `description`, `done`, `completion_time`.
4. Клиент получает `200 OK` и обновленный `TaskDto`.

Альтернативы:

| Условие | Результат |
| --- | --- |
| Задача не найдена | `404 ErrorResponse`. |
| Задача принадлежит другому пользователю | `403 ErrorResponse`. |
| Невалидное тело запроса | `400 ValidationErrorResponse`. |

## UC-05. Получение списка задач

| Поле | Описание |
| --- | --- |
| Актор | User/Admin |
| Цель | Посмотреть свои задачи. |
| Предусловия | Пользователь авторизован. |
| Постусловия | Возвращен список задач пользователя. |
| Связанные требования | FR-TASK-02 |

Основной сценарий:

1. Клиент отправляет `GET /api/v1/tasks`.
2. Backend определяет текущего пользователя.
3. Backend возвращает только задачи этого пользователя.

## UC-06. Ежедневный отчет по задачам

| Поле | Описание |
| --- | --- |
| Актор | Scheduler |
| Цель | Отправить пользователям отчет по задачам. |
| Предусловия | Настроены credentials scheduler и cron. |
| Постусловия | Email-команды опубликованы в Kafka. |
| Связанные требования | FR-SCH-01, FR-SCH-02, FR-SCH-03, FR-SCH-04 |

Основной сценарий:

1. Scheduler запускается по cron.
2. Scheduler отправляет `POST /api/v1/auth/login` с системными credentials.
3. Scheduler получает access token.
4. Scheduler запрашивает `GET /api/v1/users`.
5. Scheduler выбирает завершенные за предыдущий день и незавершенные задачи.
6. Scheduler формирует email-команды и публикует их в `EMAIL_SENDING_TASKS`.

Альтернативы:

| Условие | Результат |
| --- | --- |
| Backend недоступен | `BackendClientException`. |
| Ошибка авторизации scheduler | `SchedulerAuthenticationException`. |
| Ошибка Kafka publish | `EmailPublishingException`. |

## UC-07. Отправка email

| Поле | Описание |
| --- | --- |
| Актор | Email-sender |
| Цель | Доставить письмо пользователю. |
| Предусловия | В Kafka topic есть корректный JSON `{to, header, text}`. |
| Постусловия | Письмо отправлено через SMTP или ошибка залогирована. |
| Связанные требования | FR-EMAIL-02 |

Основной сценарий:

1. Email-sender получает сообщение из `EMAIL_SENDING_TASKS`.
2. Consumer десериализует JSON в `EmailDto`.
3. `MailService` отправляет письмо через SMTP.
4. Сервис логирует успешную отправку.
