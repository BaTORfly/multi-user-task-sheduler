# Business Requirements

## Цель продукта

Создать backend-систему для многопользовательского управления задачами, в которой пользователь может безопасно работать только со своими задачами, а система автоматически отправляет email-уведомления после регистрации и ежедневные отчеты по задачам.

## Заинтересованные стороны

| Участник | Интерес |
| --- | --- |
| Пользователь | Хранить задачи, отмечать выполнение, получать полезные уведомления. |
| Администратор | Видеть пользователей и их задачи для контроля состояния системы. |
| Владелец продукта | Получить расширяемый backend с разделением ответственности между сервисами. |
| Разработчик / DevOps | Иметь воспроизводимый запуск через Docker Compose и централизованную конфигурацию. |
| Email service | Получать корректные команды на отправку писем. |

## Бизнес-цели

| ID | Требование | Критерий достижения |
| --- | --- | --- |
| BR-01 | Пользователь должен иметь персональный список задач. | Задачи привязаны к владельцу и доступны только авторизованному пользователю. |
| BR-02 | Пользователь должен безопасно входить в систему. | Доступ к защищенным ресурсам выполняется через JWT. |
| BR-03 | Система должна уведомлять пользователя о регистрации. | После signup публикуется email-команда welcome-письма. |
| BR-04 | Система должна отправлять ежедневный отчет по задачам. | Scheduler формирует email-команды по завершенным за прошлый день и незавершенным задачам. |
| BR-05 | Администратор должен видеть пользователей с задачами. | Endpoint `/api/v1/users` доступен пользователю с ролью `ADMIN`. |
| BR-06 | Система должна быть пригодна для микросервисного запуска. | Сервисы запускаются через Docker Compose, используют Config Server и Eureka. |

## Бизнес-процессы

| Процесс | Краткое описание | Результат |
| --- | --- | --- |
| Регистрация пользователя | Клиент передает имя, фамилию, email и пароль. Backend создает пользователя и публикует welcome email. | Пользователь создан, access token возвращен, refresh token записан в cookie. |
| Авторизация | Клиент передает email и пароль. Backend проверяет учетные данные. | Клиент получает access token и refresh cookie. |
| Управление задачами | Авторизованный пользователь создает и изменяет свои задачи. | Состояние задач сохранено в PostgreSQL. |
| Ежедневный отчет | Scheduler авторизуется как системный пользователь, получает пользователей с задачами и публикует email-команды. | Email-sender получает команды и отправляет письма. |

## Бизнес-правила

| ID | Правило |
| --- | --- |
| BRule-01 | Email пользователя должен быть уникальным. |
| BRule-02 | Пользователь может работать только со своими задачами. |
| BRule-03 | Endpoint списка всех пользователей доступен только `ADMIN`. |
| BRule-04 | Задача считается завершенной, если поле `done = true`. |
| BRule-05 | В ежедневный отчет попадают задачи, завершенные за предыдущий день, и все незавершенные задачи пользователя. |
| BRule-06 | Email-команды передаются через Kafka topic `EMAIL_SENDING_TASKS`. |

## Ограничения и допущения

| ID | Описание |
| --- | --- |
| C-01 | Система реализована как backend API без пользовательского интерфейса. |
| C-02 | Для локального запуска используются Docker Compose, PostgreSQL, Kafka, Config Server и Eureka. |
| C-03 | Валидация имени и фамилии допускает только латинские буквы. |
| C-04 | Пароль должен быть не короче 8 символов и содержать строчные и заглавные латинские буквы. |
| C-05 | SMTP-доставка зависит от внешнего почтового сервера. |
